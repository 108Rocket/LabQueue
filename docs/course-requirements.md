# BMAD 作业要求与流程

依据用户提供的 `BMAD讲义+作业.pptx`，重点核对第 31–39 页。PPT 中的示例不是实际需求或用户操作授权。下列“必须”来自课程；LabQueue 的具体技术方案仍需人工评审。

## 总体门槛（第 32 页）

3–4 人一组，四周、两轮 Sprint、四个里程碑；提交完整 Git 仓库和 10 分钟演示录屏，占课程总评 30%。选题需要真实用户、至少 3 个 Epic、12 个 Story、2 条可测 NFR，以及至少 1 个并发或一致性风险点。

LabQueue 可重点分析同卡重复分配、任务重复领取、取消与启动冲突、监测后外部任务抢卡。先界定普通权限下实际能保证的范围。

## 十类交付物（第 33 页）

| 交付物 | 硬性要求 | 本次初始化状态 |
| --- | --- | --- |
| `product-brief.md` | 问题、用户、成功度量、范围外 | 输入草稿，未评审 |
| `PRD.md` | FR 编号，至少 2 条可测 NFR，范围外 | 未开始 |
| `architecture.md` | 至少 5 条 ADR，每条有否决方案及理由 | 未开始 |
| `epics.md` + Story | 至少 12 条；验收条件可直接转为断言 | 未开始 |
| `project-context.md` | 栈和版本，至少 8 条具体实现规则 | 初始草稿，待架构同步 |
| `sprint-status.yaml` | 纳入 Git，真实多次更新 | 门禁后生成 |
| 源码 + 测试 | README 可运行，每条 NFR 有测试证据 | 只有环境骨架，功能/NFR 未验证 |
| `decision-log.md` | 至少 15 条，至少 5 条真实否决或实质修改 AI 输出 | 只有真实约束来源，数量要求未完成 |
| `retrospective.md` | 度量表、实验 A 结论、实验 B 影响分析 | 空白记录模板 |
| README + 录屏 | 启动、分工、AI 声明；10 分钟视频 | 启动可用，团队/确切模型/录屏待完成 |

规划文档默认在 `_bmad-output/planning-artifacts/`，实施产物在 `implementation-artifacts/`；`decision-log.md` 和 `retrospective.md` 位于根目录。BMAD 新技能可能按工作空间生成文件夹；最终应维护课程指定名称的提交入口与上游产物链接，避免多份失去同步。

## 工作流怎么走

每个工作流使用新对话（第 30 页），先在 Codex 打开本仓库，确认 `.agents/skills` 已加载。输入“使用 bmad-help，依据 docs/course-requirements.md 判断下一步”。这是 AI 对话中的技能调用。

| 顺序 | 本仓库实际安装的技能 | 人工评审重点 |
| --- | --- | --- |
| 1 | `bmad-product-brief` | 用户、问题、指标、真实权限和范围 |
| 2 | `bmad-prd`，创建后验证 | FR/NFR、身份、外部任务、显存未知、验收指标 |
| 3 | `bmad-ux`（按需要） | 提交、等待、冲突与失败如何向用户说明 |
| 4 | `bmad-architecture` | ≥5 ADR，否决方案，身份与并发机制 |
| 5 | `bmad-create-epics-and-stories` | ≥3 Epic/≥12 Story，追溯与可测试 AC |
| 6 | `bmad-project-context` | 与架构一致，≥8 具体规则 |
| 7 | `bmad-sprint-planning`，先 readiness 再规划 | 实施就绪门禁、真实 Sprint 状态 |
| 8 | `bmad-build`、`bmad-code-review` | 按故事实现、检查、修复，更新证据与状态 |
| 9 | `bmad-correct-course` | 老师下发实验 B 变更后先做影响分析 |
| 10 | `bmad-retrospective` | 实验 A/B、度量、人工决策与局限 |

本次安装有 29 个技能。讲义中某些旧命令名可能由新技能的 action 代替；以 `bmad-help` 和本地 `SKILL.md` 为准。特别是本版本 `bmad-sprint-planning` 本身包含实施就绪检查，不需要虚构另一个不存在的技能。

## 四周节点（第 38 页）

- 第 1 周：周三前登记选题；周五 M1，PRD 评审和 5 分钟选题 pitch。
- 第 2 周：架构/ADR、Epic/Story、上下文、就绪门禁；周五 M2，架构答辩并提交 Sprint 状态。
- 第 3 周：周一收到老师的变更，当天 18:00 前交影响分析；周五 M3，核心 Epic 可运行演示。
- 第 4 周：完成剩余 Story、实验 A、复盘；周五 M4，期末演示及仓库封存，以最后一次提交为准。

M1/M2 不计分但必须通过，课程规定未通过不能进入功能实施。当前只搭环境，门禁未通过；课程开课日期未知，不能凭本机日期推算四个截止日。

## 实验 A（第 34 页）

选难度相当的两个 Story 并说明原因。X 使用 PRD、架构/ADR、项目上下文和 Story 卡，交给 `bmad-build`；Y 在干净对话中仅描述需求，不提供上游产物。两次必须同人、同日、同工具/宿主、同模型，完成后用相同 code-review 标准。

提前确认“干净对话”不会自动读取 X 的项目上下文或本仓库技能配置；必要时使用明确隔离的对照目录。不要用不同标准或故意弱化 Y。

记录五项指标：平均对话轮数、首次 review 通过率、project-context 违规次数、ADR 冲突次数、完成后返工次数。复盘分析差异来自需求、架构还是项目规则，并估算按 12 个故事是否抵得过规划投入。样本仅两个、无随机化，不能泛化为普遍因果结论；没有收益或负结果也必须如实记录。

## 实验 B（第 35 页）

第三周周一由老师给每组下发不同变更。当天 18:00 前用 `bmad-correct-course` 提交影响报告，先分析后改代码：受影响的 FR/NFR、ADR、Story、架构和工作量，人工如何接受、修改或拒绝建议。按实际评审结果在第二轮迭代完成变更。PPT 的变更示例尚未下发给 LabQueue。

## 决策与评分（第 36–39 页）

每条决策记录包括触发工作流/轮次、AI 建议与理由、人工判断及 FR/NFR/ADR 依据、改变的产物、后续验证。少于 15 条或少于 5 条真实否决/实质修改不满足门槛。初始化的用户约束不能直接伪装成已验证 ADR。

决策质量 25，追溯一致性 20，实现质量 20，工作分解 15，两项实验 15，演示 5。自定义 BMB 工作流可选加分，最多 5；并非必须安装 BMB。

持续保留适当的原始对话和提交证据；明确 AI 工具、确切模型/版本及用途。不要公开包含账号、密钥、任务私有命令或数据路径的完整会话。
