# LabQueue 工作拆分

## 概览

4 个 Epic、16 个 Story，供团队评审。首版验收使用两张模拟卡，覆盖 GATE-01 至 GATE-04 和两条 NFR。真实 L20 派发是后续条件目标，默认关闭。当前工程处于环境搭建阶段，M1、M2 和下列模拟验收均待完成。

依据工作区当前版本的 [PRD](prds/prd-LabQueue-2026-11-18/prd.md)、[架构](architecture.md)、[决策记录](../../decision-log.md)、[项目上下文](../project-context.md)和[课程要求](../../docs/course-requirements.md)。

### 架构与验收约定

- 模拟运行使用本机 SQLite、两张稳定标识的模拟 GPU、合成账号、可控时钟和故障注入。模拟执行器将用户任务参数作为数据。关键状态以已提交记录为准。
- 下文 GPU 1、GPU 2 指稳定标识。除另有说明，A 比 B 先确认入队。竞态用例用事务暂停点安排提交顺序，按已提交状态、启动事件和租约变更历史断言。
- 标为**联调验收**的断言等列出的 Story 可用后执行。原 Story 的独立验收可以先完成，联调断言仍计入对应 PRD 门槛。

### UX 设计需求

页面验收对照 [交互说明](ux-designs/ux-LabQueue-2026-11-19/EXPERIENCE.md) 和 [线框与流程](ux-designs/ux-LabQueue-2026-11-19/wireframes.md)。D-010、D-011 对应取消和刷新场景已完成文档对照，界面候选及运行验收仍待复核。Q5 的访问反馈和 Q6 的原提交手动重试候选已对照 AD-7、AD-2 和 Story 1.1、1.3。访问文案和重试交互待人工复核。模拟首版的提交字段和显存单位见 Story 1.1。

## Epic 1 · 提交并安全查看自己的任务

### Story 1.1 · 由可信身份提交任务

作为提交者，我可以登记显存未知的任务，并在提交回执丢失后重试，避免重复入队。

`FR-01、FR-02、FR-08 · NFR-02 · AD-1、AD-2、AD-7 · AC-01、AC-11`

**验收条件**

- 给定双卡忙，已认证用户提交显存未知的任务，断言任务进入排队、显存仍为未知，所有者和组来自服务端。伪造用户或组字段无法改变归属。匿名提交产生的任务数为 `0`。
- 丢弃首次成功回执后，以同一所有者和幂等键重试相同内容，断言返回原任务及原入队序号，队列只有一条记录。同键异内容被拒绝，原任务不变。
- **页面验收 · 待 UX 复核**　模拟首版接受任务名、作为数据的执行命令及未知或以 GiB 表示的正数显存估计。未知可入队，选择数值估计时空值或非正数返回字段反馈。提交成功后本人可查到该任务。

### Story 1.2 · 跨组按确认顺序排队并查看位置

作为排队者，我可以查询自己的队位，且系统时钟变化和服务重启不会改变确认入队顺序。

`FR-02、FR-03 · AD-1、AD-2 · AC-01、AC-02、AC-13 · D-003、D-011`

**独立验收**

- 用固定的双卡占用观测作为查询输入，不推进调度。不同组的 A、B 依次确认入队。分别令两者确认时间相同、B 的确认时间早于 A，断言 `seq(A) < seq(B)`，两人分别查到本人队位 `1、2`，等待原因为 GPU 被占用。应答逆序到达也不改变队位。
- 保持双卡忙并重启服务，断言原序号和队位保留。确认 C 入队，断言 `seq(C) > seq(B)`，C 的队位为 `3`。
- **页面验收 · 待 UX 复核**　本人能查到当前队位和等待原因。
- **页面乱序验收（列表、详情各跑一遍）**　扣住 B 队位为 `2` 的旧快照，令前序任务 A 离队，B 仍为排队中。在无其他写入时，从同一次提交后的快照读取两页；先送达版本更高、队位为 `1` 的完整快照，再送达旧响应，断言状态、队位、等待原因和取消入口均保留最新结果。再交叉投递：一页先收新响应，切换或重开另一页再收旧响应，旧缓存只标「上次确认」。另令仅等待原因变化（如有效观测到期），断言版本仍推进且旧原因不能覆盖；缺少可比较版本的响应也不作为当前快照。
- **快照原子性验收（列表、详情各跑一遍）**　另测读取已建立旧快照、响应尚未组装完成时，提交前序任务离队。放行读取后，断言响应仍是旧版本与旧队位；再次读取才同时得到新版本和新队位。不能把新版本贴给旧字段，反之亦然。

**联调验收 · 2.2 完成后**

- 延续重启用例，只释放一张卡并提供有效观测。断言 A 先领取该卡，B、C 仍排队且队位变为 `1、2`。
- **页面验收 · 待 UX 复核**　A 的提交者看到已获准，B、C 的提交者看到各自仍在排队。

### Story 1.3 · 隔离任务详情、私有输出和取消权限

作为提交者，我能读取自己的任务和私有输出，其他访问者无法借助已知任务 ID 或伪造身份看到这些信息或修改任务。

`FR-01、FR-03、FR-07、FR-08 · NFR-02 · AD-4、AD-7 · AC-11`

**独立验收**

- 同组非本人、异组用户和匿名访问者经列表、详情、私有输出入口访问，覆盖已知任务 ID 及伪造身份字段。用归属于本人的合成私有输出做正向对照。断言本人读到测试标记，其他访问者的越权成功数和标记泄露数均为 `0`。
- 用可观测的替身验证取消入口复用的服务端所有权检查。断言越权、匿名及伪造身份均未进入任务变更逻辑，状态、入队序号和租约维持原值。若使用会话 Cookie，缺失或无效跨站请求凭证的写入被拒绝。
- **页面验收 · 待 UX 复核**　列表、详情和私有输出不暴露他人的命令、工作目录、环境变量或日志。

**联调验收 · 3.1 和 3.2 完成后**

- 通过实际取消入口验证本人能取消排队中的 A，以及已领取但尚未确认启动的 A。两种情形都断言取消成功且启动数为 `0`，后者同时解除租约。
- 用同组非本人、异组用户、匿名及伪造身份请求复跑取消负向用例，断言越权成功、私有测试标记泄露和未经授权的状态变更均为 `0`。核对状态、入队序号和租约保持原值。
- **页面验收 · 待 UX 复核**　对无权访问者，取消反馈不暴露私有数据。

## Epic 2 · 从可靠观测派发并取得执行结果

### Story 2.1 · 等待有效观测并按最新快照恢复派发

作为排队者，我希望调度只使用最新有效观测，并在观测失效时告知等待原因。

`FR-03、FR-04 · AD-1、AD-5 · AC-04、AC-05 · D-004`

**独立验收**

- 队列非空且无租约，分别注入监测失效（含设备漏报）、过期、外部占用不明。断言三个分支均拒绝准入、查询返回对应阻塞原因。乱序样本或旧发布者样本无法覆盖当前准入状态。
- 旧有效快照显示仅 GPU 1 可用。注入故障后恢复观测，发布仅 GPU 2 可用的有效快照。断言此时可准入设备仅为 GPU 2，设备标识保持稳定。
- 在发布观测后用服务端写事务推进权威模拟时钟。截止点前观测仍有效，达到截止点时观测过期和准入代际推进同一提交，重读仍保留；重复推进或重读不重复使该观测失效，也不解除原租约。此项实现供 2.2 和 2.3 复用，跨操作的并发提交顺序在 4.1 验收。
- **页面验收 · 待 UX 复核**　本人任务能显示观测失败、过期或外部占用不可确认所导致的等待。

**联调验收 · 2.2 完成后**

- 每种监测异常下断言新增领取数为 `0`。从队列仅有一个任务且首次领取前暂停的状态执行上述恢复用例，断言恢复后新增领取恰好 `1` 次，租约绑定 GPU 2 的稳定标识。

### Story 2.2 · 原子领取队首和单卡租约

作为队首提交者，我可以在单卡可用时获得一份平台租约，多个调度尝试也只会成功一次。

`FR-01、FR-02、FR-04、FR-05 · NFR-01 · AD-1、AD-2、AD-3、AD-5 · AC-02、AC-06`

**验收条件**

- A 显存未知且仅一张卡可用时，让两个领取者并发争卡并重试。断言 A 的已获准状态、领取 ID 和租约同一提交生效，B 仍排队且队位为 `1`。
- 查询租约全历史，断言同 GPU 有效租约重叠数为 `0`，同任务同时至多持有一个有效租约。
- 用已提交模拟记录准备一个较早、已核实应回队但尚未回队的任务。让较晚任务进入实际领取写事务，断言未发租约，记录的阻塞原因是应先原序回队。2.2 实现 AD-5 的领取前检查，4.2 负责联调回队事务及恢复后的实际领取。
- **联调验收 · 2.3 完成后**　继续重试领取和启动，断言每个任务模拟启动次数 `≤ 1`，同卡租约历史仍无重叠。

### Story 2.3 · 让一次启动确认只产生一次模拟启动

作为已获准的提交者，我的任务只在当前领取通过启动裁决后执行一次。

`FR-04、FR-05 · NFR-01 · AD-1、AD-3、AD-4、AD-5 · AC-06、AC-07`

**验收条件**

- 复用 2.1 的持久模拟时钟和准入状态。启动事务取得写权后复核观测时效、准入代际、单卡资格、当前领取和执行身份，并须证实未确认、未启动、未取消且未进入待核对。前提满足时，确认和唯一模拟启动事件同一提交，原租约仍有效。
- 分别以已过期观测、失效代际、单卡资格被撤销、已取消、待核对和启动事实无法核实的状态请求启动，断言新增确认、启动和租约变更均为零。推进时钟与启动竞争的两种提交顺序在 4.1 联调。
- 丢弃回执并重放，断言读到原确认，累计启动数仍为 `1`。分别使用错误的执行身份、GPU UUID 或领取 ID，断言新增确认、启动和租约变更均为 `0`。

### Story 2.4 · 查看完成或失败并释放租约

作为提交者，我可以看到模拟执行结果，任务确认结束后原卡可再次分配。

`FR-03、FR-05、FR-06 · NFR-01 · AD-3、AD-6、AD-7 · AC-03`

**验收条件**

- 分别推进模拟任务至运行后完成、运行后 OOM。核实该次执行已结束后，断言对应终态与释放事件同一提交，有效租约数为 `0`。重放终态报告不重复释放。
- OOM 用例断言本人可查询诊断，任务参数与提交时相同，累计启动数为 `1`。
- **页面验收 · 待 UX 复核**　本人能区分运行中、已完成和失败，并看到可理解的 OOM 原因。

## Epic 3 · 在启动边界内撤回，并安全处理待核对

### Story 3.1 · 取消尚未领取的排队任务

作为排队者，我可以撤回尚未领取的任务，使它退出队列并且不会启动。

`FR-02、FR-03、FR-07、FR-08 · NFR-01、NFR-02 · AD-2、AD-4、AD-7 · AC-09 · D-010`

**验收条件**

- 双卡忙时由本人取消 A，再重放取消并释放一张卡。断言 A 始终已取消、从队列移除，新增领取和启动均为 `0`，B 队位升为 `1` 并可领取释放的卡。
- **页面验收 · 待 UX 复核**　本人取消后可见已取消状态，排队位置随退出队列更新。
- 对尚未领取的 A 重跑 Story 3.2 的「超时未受理、主动封存、入口恢复后旧请求才到达」，在封存提交后重启再放行旧请求。断言旧 ID 不使 A 出队，不创建租约或取消事件；本人手动以新 ID 发起后才取消。另测受理已提交、裁决未终结时重启：仅由服务端恢复原 ID，且最新证据仍允许取消时，原 ID 只有一个已提交终局及一次取消生效，不产生第二个请求。

### Story 3.2 · 裁决已领取任务的取消与启动竞争

作为已获准的提交者，我可以在启动确认前取消，也能在启动已确认时收到明确的截止点反馈。

`FR-02、FR-03、FR-05、FR-07、FR-08 · NFR-01、NFR-02 · AD-1、AD-2、AD-3、AD-4、AD-7 · AC-07、AC-10 · D-002、D-010、D-011`

**验收条件**

- A 已领取并停在启动确认前。令本人取消先提交，断言取消、封闭领取、解除租约同一提交，解除恰好 `1` 次。重试领取和启动后，A 仍已取消且启动数为 `0`，B 可领取释放的卡。
- 丢弃已成功提交的取消回执，先只读核对原 ID，再重放同 ID。断言可核实原终局结果、不恢复取消入口，原租约累计只解除 `1` 次，A 的启动数仍为 `0`。
- 令取消受理先提交、启动确认先于取消终局提交，断言本人取消返回已过截止点，取消产生的解除事件为 `0`，重试后累计启动数仍为 `1`，任务按执行结果流转。丢弃截止点回执后只读刷新，断言原 ID 可核实为「已过截止点」，而非仍处理中，且入口不恢复。
- **页面验收 · 待 UX 复核**　本人可在已获准且尚未确认启动时发起取消，并能区分取消成功与已过截止点。
- **取消超时、旧请求未受理**　保持 A 已获准并暂停启动，把旧 ID 请求拦在受理事务前直至超时。普通刷新查无记录：仍显示未知、请求记录与快照版本不变、不恢复入口或自动发送取消；切页或重开仍核对原 ID。本人主动「核对并封存旧取消请求」，取得较新完整快照，任务状态未变，但封存已提交且 A 仍可取消，才恢复入口。未点新取消前，放行旧请求进入服务端裁决并重放，断言因 ID 已封存被拒，任务、原租约及其历史、取消事件、请求记录和快照版本均不变。本人再手动以新 ID 取消，断言取消和释放各一次。另令受理抢先提交且尚无终局，断言核对不封存、入口仍关闭；即使旧 ID 已终结，若任务已过取消截止点也不恢复入口。
- 丢弃封存成功回执后由本人手动重复核对命令，断言返回已封存且无新增写入。另以非本人尝试封存一个确未受理、也未封存的 ID，断言拒绝且请求记录、任务、租约、取消事件和快照版本不变。
- **页面乱序验收（列表、详情各跑一遍）**　扣住 A 尚可取消的旧快照，从同一次取消提交读取两页的较新完整快照，先显示新快照再送旧响应（含 Story 1.2 的跨页交叉投递）。断言 A 仍已取消、无旧队位、等待原因和取消入口不回退。另将仅含结果的取消回执分别放在对应的完整快照之前、之后送达，断言不覆盖整页、不清除其他任务行、不启用入口；回执若提高版本下限，旧画面标「上次确认」，取得不低于该版本的完整快照才更新。旧 ID 的终局回执在新 ID 处理中到达时，不解除新请求的待核对，也不重开入口。

### Story 3.3 · 启动事实未知时保留原卡，证据恢复后按事实裁决

作为提交者，我可以知道任务正在核对，系统在查清前保留原卡并避免重复启动。

## Epic 4 · 故障恢复后保持原序并拒绝旧领取

### Story 4.1 · 按提交顺序裁决观测到期与启动

作为持有领取的提交者，我的任务能否启动取决于最终裁决时的有效观测，已确认的启动在后来到期时保留。

`FR-03、FR-04、FR-05 · NFR-01 · AD-1、AD-3、AD-4、AD-5 · AC-14 · D-006`

**验收条件**

- A 已领取且未确认启动，B 仍排队。分别注入监测失效、观测过期和外部占用不明。异常仍存在时让 B 尝试领取，并放行、重试 A 的旧启动。断言异常期间新增领取、A 新增启动确认和模拟启动均为 `0`，原租约保留至核对完成。
- 让 A 通过初检后暂停在最终裁决前，推进模拟时钟至观测截止点并先提交。断言旧领取失效，A 新增确认和启动均为 `0`。
- 反向用例中，让启动事务持有写权并完成最终核验，此时请求推进时钟。断言到期无法插入最终核验与启动提交之间，启动先提交、随后到期。此后尝试新领取和重放启动，断言新增领取、确认和启动均为 `0`，A 的已提交启动保留且累计为 `1`。
- **页面验收 · 待 UX 复核**　本人查询时能看到对应监测阻塞原因。

### Story 4.2 · 核实未启动后原序回队，阻止后到任务越过

作为已核实未启动的提交者，我可以按原入队序号回队，并在恢复时先于后到任务取得可用卡。

`FR-02、FR-03、FR-04、FR-05 · NFR-01 · AD-1、AD-2、AD-3、AD-4、AD-5、AD-6 · AC-08、AC-14、AC-15 · D-004、D-006、D-007、D-011`

**验收条件**

- 观测异常分支恢复后令 GPU 1 被外部占用、仅 GPU 2 可用。仅待核对分支令 GPU 2 也可用。让 B 实际进入领取裁决，断言其未获租约，原因是更早的 A 已核实应回队，且裁决已取得写权。以原执行身份重放 A 的启动，断言新增确认和启动均为 `0`，原租约仍保留。
