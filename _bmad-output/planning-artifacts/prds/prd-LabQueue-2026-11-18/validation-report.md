## 总体结论

四项模拟硬门槛均有可转成自动化测试的场景，两条 NFR 都有数值阈值和可采集的证据。FR-02 的时间优先排序在墙钟回拨时能颠倒系统确认顺序，FR-04 也未说明监测失效如何影响已领取、尚未启动确认的任务，这两个缺口应在相关验收口径确定前处理。现阶段结论基于文档，功能及 M1/M2 仍待验证。

## 各维度结论

- **决策就绪度** 有缺口。FR-02 写明“按系统确认入队时间升序排列”，复述了 D-001 已记录的排序表述，但缺少能兑现用户最新澄清的约束。FR-07 及 AC-07、AC-10 与 D-002 一致，保留了领取后、启动确认前的本人取消权，并定义两种确认顺序。
- **内容实质** 扎实。两条 NFR 各自给出三个必须为 0 的指标，并使用与调度恢复及跨用户隐私直接相关的故障注入和账号矩阵。性能指标保留候选状态，PRD 记录待定的阈值、负载和基线。
- **目标与范围一致性** 扎实。UJ-01 从双卡忙时排队到资源允许时获准和取得终态，贯穿 FR-01 至 FR-08。首版聚焦可重复的模拟闭环，FR-09/AC-12 将真实启动限制为经架构评审和服务器前置验证的条件目标。度量边界明确保留平台外占用的不确定性。
- **验收清晰度** 有缺口。GATE-01（AC-01 至 AC-03）可断言跨组位置、等待原因、单卡释放后的获准和终态，以及未知显存、OOM 和租约释放。GATE-02（AC-04/05）可断言三类监测异常时无新增派发，并用恢复时交换占用的方式检查新观测确实驱动派发。GATE-03（AC-06 至 AC-08）可断言租约互斥、启动次数上限、取消与启动的两种确认顺序和超时但启动结果未知时的阻塞。GATE-04（AC-09 至 AC-11）可断言本人取消和越权请求拒绝、私有字段未泄露及目标状态未改变。各门槛仍需实现测试并采集实际结果。
- **范围透明度** 足够。首版范围和 AC-12 符合 PRD 工作区记忆记录及当前用户决定。模拟闭环为必做，真实 L20 派发有独立启用条件，GitHub 为唯一交付渠道，汇报、录屏和实验 B 排除。普通权限、提交者所属执行身份、外部任务不受平台强制管控和未知显存准入均保留。
- **下游可用性** 足够。术语给出入队确认、有效观测、派发领取、平台租约和启动确认，FR 与 AC 的连接足以供架构及故事拆分。第 102 行明确区分实际启动边界和异步回执，支持后续取消裁决设计。需要在解决两个高优先级问题时明确将“派发”拆成是否领取、是否启动确认、是否发生执行副作用三种可观察事件，避免测试和状态机使用不同含义。
- **文档形式适配** 扎实。单条用户旅程为内部排队工具保留提交至终态的主路径，主要篇幅用于能力、边界与验收条件。团队可以从 FR、AC、NFR 抽取架构与故事输入，且真机依赖已被约束在条件目标。

### 高（2）

**墙钟回拨会逆转全局 FIFO**

[FR-02](prd.md#提交查询与顺序)、AC-01/02、[D-001](../../../../decision-log.md)。A 先由系统确认且时间为 10:00:05，回拨后 B 才确认且时间为 09:59:55。若直接用墙钟时间作主键，B 会先排队并先获准，以序号仅处理同时间的规则在此不起作用。建议把产品断言写为按系统确认顺序领取，由架构决定使用随成功确认严格递增且持久的全局序号，或能保证相同次序的逻辑确认键。序号须体现最终确认顺序，不能在并发提交开始时取号后任由确认顺序反转。建议用可控时钟覆盖回拨、同刻及并发确认，分别检查用户位置和释放单卡后的首次领取对象。

**监测失效发生在领取之后时缺少规则**

[FR-04/05](prd.md#资源准入与执行)、FR-07、AC-04/05/08/10。AC-04 的前置条件为“无平台租约”，因此新增派发为 0 无法说明已有租约的执行方还能否确认或触发启动。请用户决定启动确认是否须重新取得当前有效观测，故障期间如何展示任务状态和原因，租约保留多久或在何种证明下撤销，以及撤销后是按原确认次序重排、重新确认入队还是结束为失败。恢复时同一 GPU 仍空闲、已被外部任务占用、其他 GPU 可用三条分支也需明确。建议优先比较启动前暂停并保留租约、确认从未启动后撤销租约的方案，分别权衡阻塞容量和恢复复杂度。FR-05 已约束实际执行状态未知时不能因超时就启动或重新分卡，FR-07 已约束启动确认前本人仍可取消，以及取消先成功时启动数为 0、租约解除，这两条作为补测的既定约束。

### 中（4）

**监测边界需要断言领取和启动两个事件**

AC-04/05/08/10。建议在 A 领取 GPU 1、B 排队、A 被确定性暂停在启动确认前时，依次注入监测失败、过期、外部占用不明，分别记录新领取、启动确认、模拟执行副作用、租约变化和用户可见原因。按用户选定规则断言故障期间 A 的确认与实际启动数、租约和恢复状态，并测恢复后同卡空闲、外部占用、仅另一卡可用。故障期间让 A 本人取消，再放行旧执行者重试，验证取消先成功时 A 启动 0 次且租约解除，监测未恢复时 B 新领取为 0。再变体让启动结果未知且跨越租约超时，断言未查清前无重复启动或同卡再分配。

**一致性证据需要证明注入点确实发生且系统可推进**

AC-06、[NFR-01](prd.md#可测非功能需求)。建议用控制点记录领取成功、取消已确认但未响应、模拟启动已发生但无回执三个注入位置，关联恢复后的实际重放。用跨重启保留、可独立核查的执行器启动事件和租约历史，按任务 ID、GPU 稳定标识和租约 ID 对账。为 AC-06 加一个有效观测下必有一位胜出、任务能启动一次的正向断言，以发现全被阻塞但零冲突的假通过。对结果未知的窗口单独断言该卡新增派发为 0。

**隐私证据需要落实出口和状态快照**

AC-11、NFR-02。建议用同组、异组、未认证及伪造身份请求覆盖已实现的列表、详情、取消及私有输出入口。每类字段放入独立合成标记，保存脱敏响应和请求前后的任务状态、顺序与租约摘要。本人能读标记且在启动确认前能取消作为正向对照，避免测试数据或入口缺失造成零泄露假象。

**下游团队可能沿用较早的交付要求**

[课程要求](../../../../docs/course-requirements.md)、[README](../../../../README.md)、[分工方案](../../../../docs/team-allocation.md)。PRD 第 23 行已经体现用户决定。关联文件中仍出现 10 分钟录屏、最终演示与实验 B，课程文档末尾只覆盖部分变更。建议后续同步当前执行口径并给原始课件摘要标明出处。

## 四项模拟门槛

- **GATE-01 · AC-01～03** 具备正常路径、同时间决胜、成功和 OOM 的可断言脚本条件。用可控墙钟复现 A 先确认、B 在回拨后确认，核对位置 A=1、B=2。随后仅释放一张卡，断言 A 先领取。保留同时间用例，并补并行提交与重启后顺序一致性。
- **GATE-02 · AC-04～05** 无租约时的三种监测异常和恢复后改用最新可用卡可直接转成测试。已领取、启动确认前的路径缺少产品预期。 AC-05 建议在首次领取前暂停调度来注入故障，恢复后只推进一个待领取任务，单独统计恢复窗口内的 1 次派发。
- **GATE-03 · AC-06～08** 可用同步屏障驱动两个领取者争同一卡，分别固定取消先与启动先的顺序，并模拟启动结果未知及租约超时。AC-06 补至少一次成功领取和可控启动的正向断言，避免系统一直停摆也通过。
- **GATE-04 · AC-09～11** 可覆盖排队中取消、已领取但未确认启动时取消、第三方越权。保留旧领取者重试，核对被取消任务启动数为 0、租约解除、B 只在有效观测下接手。

## 领取后监测失效 · 待用户决定

- 启动边界。领取时的有效观测是否足够，还是启动确认前也必须重新取得有效观测？选择暂缓可避开沿用已失效观测带来的风险，同时会延迟任务启动。 真实派发仍受观测异常时停止新增派发的约束，启用前须明确启动确认是否属于这条约束的边界。
- 租约和排位。若暂缓启动，是保留原租约等待复核，还是确认尚未开始后撤销领取？若撤销，任务是保留原确认顺序回队，还是进入用户可见的失败终态？保留租约需明确最长等待、超时后的核对和状态提示。回队需明确旧领取失效和 FIFO 排位。
- 恢复条件。新观测显示原卡仍可用时，是否允许原领取继续？原卡已被外部进程占用、另一张卡空闲时，是等待原卡，还是按队列重新领取并允许换卡？同时确认 A、B 的可见状态和阻塞原因。

## 领取后监测失效 · 建议补测

- 固定时序。让 A 持有效租约停在启动确认前、B 排队，分别注入监测报错、观测过期、外部占用不明，再放行原领取者并重试。断言异常期新增领取为 0、同卡至多一个有效平台租约、同任务至多一次启动。A 是否可启动以及租约、状态、位置的断言，按用户最终选定的策略填写。
- 恢复分支。分别恢复为原卡仍可用、原卡已被外部占用且另一张卡可用。记录最新观测所指稳定 GPU 标识、实际领取顺序、各卡租约变化与 A/B 状态。若选择撤销并回队，重放旧领取的启动请求并验证其不能生效。
- 取消与未知结果。异常期间安排 A 的所有者先于启动确认成功取消，断言 A 已取消、启动为 0、租约解除，旧领取者重试无效，B 在监测仍失效时领取为 0。另模拟启动请求已发出但结果未知、租约超时，断言状态核实前原任务新增启动数和原卡新增派发数都为 0。

## 两条 NFR 的取证

- **NFR-01 · 故障恢复一致性** 可取证。分别在领取成功后、取消确认成功但响应前、模拟启动已记录但回执未到时中断并恢复。保存跨重启可核对的模拟执行器启动事件和有序租约事件，至少含任务 ID、GPU 稳定 ID、租约 ID 及事件顺序。逐例报告重复启动、同卡租约重叠、已取消任务启动三个 0。未知窗口另报告该卡新增派发为 0，并用正向对照证明故障钩子命中、状态明朗后可继续推进。
- **NFR-02 · 跨用户隐私隔离** 可取证。为任务的命令、路径、环境和日志设置无敏感内容的唯一标记，使用同组非本人、异组、未认证和伪造身份请求覆盖列表、详情、取消及已实现的私有输出入口。保存脱敏响应和请求前后状态、队列位置与租约快照，逐例核对越权成功、标记泄露、未授权变更三个 0。用本人读取同一标记及合法取消作正向对照，并在证据中列清实际覆盖的入口。

## 针对性复验（2026-11-18）

初验发现和等级按当时审阅的草稿保留。以下结论针对 D-003、D-004 写入后的 FR-02、FR-04、FR-07 和 AC-13～15，并参照 FR-05、AC-07、AC-08、AC-10 核对两条异常路径。**本次只核对需求与验收文本。模拟测试尚未运行。**

### 初验缺口 1 · 全局 FIFO 被墙钟回拨打乱 · 文档层已关闭

FR-02 以持久化的全局入队序号体现实际确认顺序。AC-13 让 B 在回拨后确认，核对 A、B 的序号和排位，重启后再确认 C 并核对序号续增，最后释放单卡并断言 A 先领取。AC-15 按原序号让 A 先于 B 重新领取，与 FR-02 的回队规则一致。证据待模拟运行。

### 初验缺口 2 · 领取后监测失效缺少行为规则 · 部分关闭

FR-04 与 AC-14、AC-15 一致覆盖已核实未启动的任务。监测异常时阻断新领取和未确认的启动，撤销原领取并解除原租约，按原顺序回队。恢复后按最新有效观测换卡，旧领取在新租约生效后仍无法启动。以下两个分支尚缺直接验收断言，缺口未完全关闭。

- **取消先成功后重放恢复，未关闭。** FR-02 要求取消成功的任务移出队列，FR-07 将其置为已取消且解除已有租约。FR-04 的回队条件只写了尚未通过启动确认及已核实未启动，未明确排除已取消终态。AC-14、AC-15 未覆盖恢复与取消的交错，AC-07、AC-10 也未重放监测恢复。建议明确恢复写入时须核验任务仍符合回队条件，已取消终态不可回队。补测让 A 已领取且监测失效，令取消先确认成功，再重放旧恢复和旧启动请求，随后恢复观测。断言 A 始终已取消、队列中无 A、新领取数和启动数为 0、有效租约数为 0，B 可在有效观测下领取。
- **启动结果未知后租约超时，未关闭。** FR-04 只允许在核实未启动后走撤销回队分支。FR-04、FR-05 和 AC-08 约束核实前零重启、零重派，但 AC-08 只观察这两个结果。即使错误地提前释放租约，其他派发门槛也可能让测试得到两个零。建议明确超时后仍保留原租约对 GPU 的占用，直到执行结果得到核实。补测让 A 的启动结果未知且租约超时，再让监测恢复并报告 GPU 1 可用，保持 B 排队。核实前断言原租约释放事件为 0、该卡仍由原租约阻挡、A 未回队、A 新启动和该卡新增领取均为 0。
