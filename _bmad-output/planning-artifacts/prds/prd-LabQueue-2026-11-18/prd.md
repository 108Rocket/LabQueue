# LabQueue 产品需求文档

本草稿供团队评审和后续架构设计使用。范围和四项硬门槛来自用户已确认的简报内容，排序与并发取消规则由用户在 PRD 工作流中确认。M1、M2 和本文验收均待完成，当前应用处于环境搭建阶段。[产品简报](../../product-brief.md) · [课程要求](../../../../docs/course-requirements.md) · [项目上下文](../../../project-context.md) · [决策记录](../../../../decision-log.md)

## 用户与目标

不同研究组的研究生共用一台装有两张 L20 的服务器。两张卡都忙时，提交者可以登记任务、查询自己当前的位置和等待原因，必要时在启动确认前撤回。资源允许时，系统按确定的顺序派发，让提交者看到任务如何结束。

**UJ-01 等卡并获得结果。** 基于简报中的真实等待经历，研究生在两张卡均忙时提交任务并查看排队状态。可用卡出现后，队首任务获准启动，提交者可以查看完成或失败状态。研究生也可以在启动确认前取消本人的任务。

## 首版范围

- **必做**：通过模拟资源源和执行器验证提交、排队、派发、运行、完成或失败，以及取消、权限隔离、监测异常与并发恢复。四项硬门槛全部通过才算模拟闭环验收通过。
- **条件目标**：在同一台 L20 服务器上，以提交者自己的执行身份启动一个受控任务。FR-09 定义启用条件。
- **范围外**：复杂组间公平策略、组内轮转、使用统计和完整审计分析、多服务器调度、分布式多卡任务、同卡多任务、自动显存峰值预测、自动改 batch 或自动重跑 OOM 任务、以管理员权限改造服务器或管控平台外任务。
- **交付**：GitHub 仓库是唯一交付渠道。M4 模拟验收证据应可复现并明确标记为模拟。汇报、录屏及实验 B 在交付范围外。

## 术语

| 术语 | 定义 |
| --- | --- |
| 入队确认 | 系统接受提交，并按确认发生的先后确定唯一且持久的全局入队序号。确认入队时间用于展示和审计。 |
| 平台租约 | 一个任务对一张 GPU 的平台内使用权。每张 GPU 同时至多有一个有效平台租约。 |
| 派发领取 | 系统为队首任务获得平台租约并将其标为已获准。领取之后仍可能取消。 |
| 启动确认 | 系统确认任务进入不可再取消排队的启动边界。若取消已先成功，执行方不得在此边界前后产生启动。 |
| 有效观测 | 当前调度所依赖的资源观测成功、未过期，且平台能够确认外部占用情况。 |

## 功能需求

### 提交、查询与顺序

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| FR-01 | 已认证的用户可以提交并查询自己的任务。系统依据可信身份确定所有权。显存估计可以标为未知，未知任务仍可申请一张完整 GPU 的平台使用权。 | AC-01、AC-02、AC-11 |
| FR-02 | 首版使用跨研究组的全局 FIFO，按系统实际确认入队的先后排序。入队序号随确认顺序严格递增，重启后保留。确认入队时间不参与排序，时钟回拨或时间相同均不改变顺序。有可派发容量时，优先领取队首任务。按 FR-04 回队的任务保留原入队序号，取消成功的任务从队列移除。 | AC-01、AC-02、AC-10、AC-13、AC-15 |
| FR-03 | 提交者可查询本人的排队位置（从 1 开始）及当前等待原因，并可区分排队中、已获准、运行中、已完成、失败和已取消。监测异常作为阻塞原因显示。失败时提供可理解的原因。 | AC-01、AC-03、AC-04、AC-05、AC-10 |

### 资源准入与执行

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| FR-04 | 用稳定标识区分两张 GPU。调度仅在有效观测下领取任务，使用经确认可用且无有效平台租约的 GPU，启动确认时也必须有当前有效观测。监测失效、数据过期或外部占用不明时暂停新增领取，并阻止尚未通过启动确认的已有领取继续确认或触发实际启动。对尚未通过启动确认、已核实未启动且未取消的任务，撤销原领取并解除其租约，按原入队序号回队。恢复流程写入回队状态时，必须核验任务仍符合回队条件。取消确认先成功的任务保持已取消，重放旧恢复请求也不得使其回队。旧领取失效，监测恢复或任务重新领取后也不能凭旧领取通过启动确认或启动。执行结果未知时按 FR-05 核对，核实前不得再次启动或重新分配该卡。恢复后按最新有效观测和全局 FIFO 重新领取，允许领取另一张可用 GPU。 | AC-02、AC-04、AC-05、AC-08、AC-14、AC-15 |
| FR-05 | 并发领取、取消、重试和崩溃恢复均须维持每卡最多一个有效平台租约、每任务最多一次启动。执行状态未查清时必须继续保留该卡的平台占用。启动结果未知时，即使租约超时且监测已恢复并显示该卡可用，也须保留至执行状态得到核实。期间不得解除该保留、重新分配该卡或再次启动原任务。 | AC-06、AC-07、AC-08、NFR-01 |
| FR-06 | 模拟执行应支持完成和失败两种结果。任务结束得到确认后，应记录对应终态并释放其平台租约。模拟 OOM 以失败结束并提供诊断，不自动修改任务参数或重跑。 | AC-03、NFR-01 |

### 取消和访问控制

| 编号 | 需求 | 验收 |
| --- | --- | --- |
| FR-07 | 提交者可以在启动确认成功前取消本人的任务，包括已派发领取且尚未启动确认时。取消确认先成功时，任务进入已取消、启动次数为 0，已有租约随取消解除。启动确认先成功时，取消排队请求返回已过截止点，任务按执行结果流转。 | AC-07、AC-09、AC-10 |
| FR-08 | 服务端应检查任务所有权。非所有者不能查询任务详情、取消任务或读取私有命令、工作目录、环境变量和日志。客户端声明的用户或组不能授予权限。 | AC-11、NFR-02 |

### 真实 L20 派发（条件目标）

**FR-09** 经架构评审与服务器验证后，才允许真实派发。验证应覆盖提交者所属的执行身份、外部占用可见性、启动与取消确认边界、租约及故障恢复。普通权限下只能保证平台内租约约束，平台外任务可随时占用 GPU。真实派发不得依赖切换他人 Linux 身份、共用后端所有者身份、管理员权限或终止平台外进程。

**AC-12（条件验收）** 启用前有架构评审及上述服务器前置条件的验证记录。满足条件后，在 L20 上受控完成一次提交、启动和终态确认，核对运行身份属于提交者，并验证监测异常时新增真实派发为 0。无法确认前置条件时，真实派发保持停用。AC-12 不计入模拟验收门槛。

## 四项模拟验收硬门槛

### GATE-01 排队可见

- **AC-01** 两张模拟卡都忙。不同研究组的用户先后提交任务 A、B，A 的显存估计未知。断言两个任务均入队，提交者分别看到本人的位置为 1、2，等待原因是 GPU 被占用，A 的显存估计仍显示未知。
- **AC-02** 释放且观测确认其中一张卡可用。断言未知显存的 A 获准并获得该卡的平台租约，B 仍排队且位置更新为 1。再让 A、B 的确认入队时间相同，断言先确认的 A 获得较小入队序号并先获准，两张卡均保持原稳定标识。
- **AC-03** 分别配置模拟执行完成和模拟 OOM 失败。断言用户可见运行及相应终态，结束确认后对应租约数为 0。OOM 用例断言原因可见、参数原样保留、启动次数为 1。
- **AC-13** 两张模拟卡均忙。先确认 A 入队，再回拨可控墙钟并确认 B 入队，使 B 的确认时间早于 A。断言 A、B 的入队序号按确认先后递增，位置分别为 1、2。重启服务时保持两卡忙，断言两个原序号和队位不变。再确认 C 入队，断言 C 的序号大于 B，队位为 3。只释放一张卡并提供有效观测，断言 A 先领取，B、C 仍排队。

### GATE-02 异常时暂停派发

- **AC-04** 保持队列非空且无平台租约，分别注入监测失效、数据过期、外部占用不明三种情形。每种情形内新增派发次数均为 0，用户可以看见对应的阻塞原因。
- **AC-05** 队列仅有一个等待任务。在首次领取前暂停调度，保留最后一次有效观测为 GPU 1 可用、GPU 2 被占用，并注入监测故障。恢复监测时交换两卡的占用情况并推进调度。断言恢复后新增派发恰好 1 次，使用最新有效观测中可用的 GPU 2。用例中的卡号指各自的稳定标识。
- **AC-14** 让先入队的 A 领取 GPU 1，并把执行器停在启动确认前，B 继续排队。分别注入监测失效、观测过期和外部占用不明；每种异常仍存在时让 B 尝试领取，放行 A 的旧领取者并重试。断言异常期间新增领取、A 的成功启动确认和实际模拟启动均为 0。核实 A 未启动后，断言原领取失效、原租约解除，A 按原入队序号回到 B 前面，且提交者能看到监测阻塞原因。另从 A 已领取且监测失效的状态重测。捕获准备让 A 回队的恢复请求，在它写入前让 A 的取消确认先成功，再重放该旧恢复请求。断言 A 仍为已取消、队列中无 A、A 的模拟启动次数为 0。
  - **初检后过期**：令 A 通过初检但尚未到达最终启动裁决，推进模拟时钟至观测截止点，使过期先提交，再放行启动。断言该领取失效、A 的新增启动确认与新增模拟启动均为 0。另测启动事务在有效观测下完成最终核验并持有写权时请求推进时钟：过期不能在最终核验和启动提交之间生效；启动先提交、其后过期，再尝试领取和重放启动，断言无新增领取或启动，A 已提交启动不撤销且累计启动数仍为 1。
- **AC-15** 以 AC-14 中领取已失效且已核实应回队的 A 为起点，使核实证据对调度可读，在 A 的回队事务取得写权前暂停它。恢复监测使 GPU 1 被外部占用、GPU 2 成为唯一可用卡。先让 B 进入领取裁决，断言因 A 待回队而非忙锁未取得租约。放行 A 回队后，断言 A 的原序号不变，先于 B 领取 GPU 2 并取得新租约，B 仍排队。
  - **旧领取重放**：另测 GPU 1 已恢复可用但 A 的旧租约尚未解除，重放旧领取的启动确认和启动，断言新增确认与启动均为 0，旧保留及其变更历史不变。再从 A 已换领 GPU 2 的状态重放旧启动、心跳、结果与释放请求，断言无新确认或启动、无状态迁移，新租约记录及其变更历史不变。推进新领取，断言只在 GPU 2 启动一次。
  - **取消先于回队**：从 A 已核实应回队但回队尚未取得写权的状态重测，令恢复后的最新观测仅显示 A 的原卡 GPU 1 可用。先成功取消 A，断言取消与解除原租约同提交，再重放已准备的恢复请求。断言 A 仍已取消、未回队、无新租约且启动数为 0；B 不被 A 的旧领取挡住，获得 GPU 1 租约。

### GATE-03 并发时避免重复启动

- **AC-06** 两个领取尝试同时争用同一张可用模拟卡，随后重试领取和启动。根据租约变化记录断言有效期没有重叠，并核对每个任务的模拟启动次数 ≤ 1。
- **AC-07** 对同一已领取任务分别安排取消确认先成功、启动确认先成功，再重试领取与启动。取消先成功时断言终态为已取消、启动数为 0、已有租约失效。启动先成功时断言拒绝取消排队，模拟执行推进后启动数为 1。
- **AC-08** 让 A 领取 GPU 1 后进入启动结果未知状态，B 继续排队。推进至 A 的租约超时，再恢复监测并报告 GPU 1 可用，保持 A 的启动结果未知。核实执行状态前，核对 GPU 1 对 A 的平台保留仍在，保留解除事件数为 0。尝试将 GPU 1 分配给 B，断言该卡因原保留无法重新分配，B 未获得该卡租约。重试 A 的启动，断言 A 新增模拟启动次数为 0。
  - **证据恢复，原领取未因观测失效（B1-R1）**：另测先入队的 A 已领取 GPU 1 但尚未确认启动，故障仅屏蔽启动事实的权威核对，使 A 进入待核对。核对期间保持观测有效、准入代际和 GPU 1 的监测资格不变，租约未超时，不请求取消。核对受阻时，令 GPU 1 为唯一观测可用卡，尝试恢复、重试启动和让 B 领取，断言 A 仍待核对、原租约未解除、B 不能领取原卡，A 无新增确认或启动。恢复可供裁决方读取的权威证据并核实 A 未通过启动确认、未启动且未取消，在回队事务取得写权前暂停它。令 GPU 2 也可用，以原执行身份重放启动并让 B 进入领取裁决：A 因待核对而不能新增确认或启动、原租约仍保留，B 因 A 待回队而非忙锁未取得租约。再放行恢复事务，从同一提交的状态与事件断言旧领取已封闭并撤销、原租约解除一次、A 以原入队序号回到 B 前且尚未启动。重新派发时令 GPU 1 再次成为唯一可用卡，断言 A 先于 B 领取 GPU 1，执行身份不变但领取 ID 不同。重放针对旧领取的启动、释放和恢复请求，断言无新增确认或启动、无状态迁移，新租约及其变更记录不变；推进新领取后，断言唯一已提交的启动确认和模拟启动事件均属于新领取 ID。
  - **待核对记录未提交（B1-R1）**：在原领取未失效时，让启动事实暂不可核实，并使待核对记录提交失败。恢复证据为可读且证实未确认、未启动；在补记待核对或封闭旧领取前重放旧启动并尝试新增领取，断言准入仍关闭、无新增领取或启动、原租约未解除。另测在此点重启并恢复有效观测，断言旧未确认领取已因代际推进失效，重放不能启动或改写租约。
  - **证据恢复为已确认（B1-R1）**：先提交唯一启动确认和模拟启动事件，再丢失回执、暂时屏蔽权威证据。只恢复启动证据，不提供终态证据。尝试回队、本人取消和重放启动，断言 A 未回队、取消返回已过截止点、原租约仍保留、原确认与启动事件保留且启动累计仍为一次。

### GATE-04 取消与权限

- **AC-09** 两卡均忙时取消本人的排队任务。释放卡后断言该任务已取消、启动数为 0。
- **AC-10** 让 A 获得租约并停在启动确认前，B 仍排队。断言 A 的所有者可取消，随即核对 A 的启动数和有效租约数均为 0，并确认 B 在有效观测下可获得释放的卡。
  - **取消先于待核对回队（B1-R1）**：从 AC-08 的证据已恢复、回队事务尚未取得写权、原领取未因观测失效的时序分支，令 GPU 1 为唯一观测可用卡。先让 A 的所有者取消，再放行并重放针对旧领取的恢复请求。断言取消和原租约解除同提交、只解除一次，A 始终已取消、未回队、未获新租约、启动数为 0；B 获得已释放的 GPU 1 租约。
- **AC-11** 同组、异组和未认证访问者分别尝试查询其他人的任务详情、取消任务或读取其私有字段，其中包括伪造用户或组声明的请求。断言越权成功数和私有字段泄露数均为 0，且他人任务状态、顺序和租约保持原值。

## 可测非功能需求

| 编号 | 质量目标与阈值 | 测试条件与断言 |
| --- | --- | --- |
| NFR-01 故障恢复一致性 | 全部故障注入用例中，重复启动数、同卡租约重叠次数、已取消任务启动数均为 0。 | 本地使用两张模拟卡及至少两个任务，分别在领取成功后、取消确认成功但响应前、模拟启动已记录但回执未到时中断服务。每个用例恢复后重放相应操作，从模拟启动事件和租约变化记录核对三个指标。执行状态未知时，另断言该卡新增派发数为 0。关联 FR-05、FR-07。 |
| NFR-02 跨用户隐私隔离 | 所有负向权限用例中，越权成功数、私有测试标记泄露数、未经授权的状态变更数均为 0。 | 使用同组两账号、异组一账号和未认证会话。在列表、详情、取消响应和可用的私有输出入口检查私有测试标记，覆盖使用已知任务标识及伪造所有者或组字段两类请求。正向对照须验证提交者能读到自己的测试标记，也能在启动确认前取消本人的任务。关联 FR-01、FR-08。 |

## 验收证据与未决事项

- **通过标准**：GATE-01 至 GATE-04 全部通过，两条 NFR 全部达标。用例应记录模拟环境、输入、预期、实际结果及对应需求编号。证据提交 GitHub 时使用合成数据。当前结果均为待验证。
- **产品度量边界**：可比较模拟用例覆盖和通过情况。实际排队时长受平台外占用影响，本版无固定等待时长承诺，全局 FIFO 也无组间公平保证。队列查询性能保留为候选 NFR，阈值、负载与基线待确定。
- **架构评审输入**：可信身份与组关系来源、有效观测的时效阈值、领取与租约的一致性、启动确认如何约束执行方，以及崩溃后的状态核对。真实派发的启动确认须与不可撤销的启动边界一致，异步回执抵达时间本身不能用于裁决取消先后。
- **产品待确认**：启动确认后的运行中终止属于另一个操作，本草稿仅为排队取消设定必做验收。条件目标启用前须确认运行中的终止权限、执行身份与进程归属。
