# PRD Quality Review — LabQueue

## Overall verdict

四项模拟硬门槛均有可转成自动化测试的场景，两条 NFR 都有数值阈值和可采集的证据。FR-02 的时间优先排序在墙钟回拨时能颠倒系统确认顺序，FR-04 也未说明监测失效如何影响已领取、尚未启动确认的任务，这两个缺口应在相关验收口径确定前处理。现阶段结论基于文档，功能及 M1/M2 仍待验证。

## Decision-readiness — thin

FR-02 写明“按系统确认入队时间升序排列”，复述了 D-001 已记录的排序表述，但缺少能兑现用户最新澄清的约束。FR-07 及 AC-07、AC-10 与 D-002 一致，保留了领取后、启动确认前的本人取消权，并定义两种确认顺序。

### Findings

- **high** 墙钟回拨会逆转全局 FIFO（[FR-02](prd.md#提交查询与顺序)、AC-01/02、[D-001](../../../../decision-log.md)）— A 先由系统确认且时间为 10:00:05，回拨后 B 才确认且时间为 09:59:55。若直接用墙钟时间作主键，B 会先排队并先获准，以序号仅处理同时间的规则在此不起作用。建议把产品断言写为按系统确认顺序领取，由架构决定使用随成功确认严格递增且持久的全局序号，或能保证相同次序的逻辑确认键。序号须体现最终确认顺序，不能在并发提交开始时取号后任由确认顺序反转。建议用可控时钟覆盖回拨、同刻及并发确认，分别检查用户位置和释放单卡后的首次领取对象。
- **high** 监测失效发生在领取之后时缺少规则（[FR-04/05](prd.md#资源准入与执行)、FR-07、AC-04/05/08/10）— AC-04 的前置条件为“无平台租约”，因此新增派发为 0 无法说明已有租约的执行方还能否确认或触发启动。请用户决定启动确认是否须重新取得当前有效观测，故障期间如何展示任务状态和原因，租约保留多久或在何种证明下撤销，以及撤销后是按原确认次序重排、重新确认入队还是结束为失败。恢复时同一 GPU 仍空闲、已被外部任务占用、其他 GPU 可用三条分支也需明确。建议优先比较启动前暂停并保留租约、确认从未启动后撤销租约的方案，分别权衡阻塞容量和恢复复杂度。FR-05 已约束实际执行状态未知时不能因超时就启动或重新分卡，FR-07 已约束启动确认前本人仍可取消，以及取消先成功时启动数为 0、租约解除，这两条作为补测的既定约束。

## Substance over theater — strong

两条 NFR 各自给出三个必须为 0 的指标，并使用与调度恢复及跨用户隐私直接相关的故障注入和账号矩阵。性能指标保留候选状态，PRD 记录待定的阈值、负载和基线。

## Strategic coherence — strong

UJ-01 从双卡忙时排队到资源允许时获准和取得终态，贯穿 FR-01 至 FR-08。首版聚焦可重复的模拟闭环，FR-09/AC-12 将真实启动限制为经架构评审和服务器前置验证的条件目标。度量边界明确保留平台外占用的不确定性。

## Done-ness clarity — thin

GATE-01（AC-01 至 AC-03）可断言跨组位置、等待原因、单卡释放后的获准和终态，以及未知显存、OOM 和租约释放。GATE-02（AC-04/05）可断言三类监测异常时无新增派发，并用恢复时交换占用的方式检查新观测确实驱动派发。GATE-03（AC-06 至 AC-08）可断言租约互斥、启动次数上限、取消与启动的两种确认顺序和超时但启动结果未知时的阻塞。GATE-04（AC-09 至 AC-11）可断言本人取消和越权请求拒绝、私有字段未泄露及目标状态未改变。各门槛仍需实现测试并采集实际结果。

### Findings

- **medium** 监测边界需要断言领取和启动两个事件（AC-04/05/08/10）— 建议在 A 领取 GPU 1、B 排队、A 被确定性暂停在启动确认前时，依次注入监测失败、过期、外部占用不明，分别记录新领取、启动确认、模拟执行副作用、租约变化和用户可见原因。按用户选定规则断言故障期间 A 的确认与实际启动数、租约和恢复状态，并测恢复后同卡空闲、外部占用、仅另一卡可用。故障期间让 A 本人取消，再放行旧执行者重试，验证取消先成功时 A 启动 0 次且租约解除，监测未恢复时 B 新领取为 0。再变体让启动结果未知且跨越租约超时，断言未查清前无重复启动或同卡再分配。
- **medium** 一致性证据需要证明注入点确实发生且系统可推进（AC-06、[NFR-01](prd.md#可测非功能需求)）— 建议用控制点记录领取成功、取消已确认但未响应、模拟启动已发生但无回执三个注入位置，关联恢复后的实际重放。用跨重启保留、可独立核查的执行器启动事件和租约历史，按任务 ID、GPU 稳定标识和租约 ID 对账。为 AC-06 加一个有效观测下必有一位胜出、任务能启动一次的正向断言，以发现全被阻塞但零冲突的假通过。对结果未知的窗口单独断言该卡新增派发为 0。
- **medium** 隐私证据需要落实出口和状态快照（AC-11、NFR-02）— 建议用同组、异组、未认证及伪造身份请求覆盖已实现的列表、详情、取消及私有输出入口。每类字段放入独立合成标记，保存脱敏响应和请求前后的任务状态、顺序与租约摘要。本人能读标记且在启动确认前能取消作为正向对照，避免测试数据或入口缺失造成零泄露假象。

## Scope honesty — adequate

首版范围和 AC-12 符合 PRD 工作区记忆记录及当前用户决定。模拟闭环为必做，真实 L20 派发有独立启用条件，GitHub 为唯一交付渠道，汇报、录屏和实验 B 排除。普通权限、提交者所属执行身份、外部任务不受平台强制管控和未知显存准入均保留。

### Findings

- **medium** 下游团队可能沿用较早的交付要求（[课程要求](../../../../docs/course-requirements.md)、[README](../../../../README.md)、[分工方案](../../../../docs/team-allocation.md)）— PRD 第 23 行已经体现用户决定。关联文件中仍出现 10 分钟录屏、最终演示与实验 B，课程文档末尾只覆盖部分变更。建议后续同步当前执行口径并给原始课件摘要标明出处。

## Downstream usability — adequate

术语给出入队确认、有效观测、派发领取、平台租约和启动确认，FR 与 AC 的连接足以供架构及故事拆分。第 102 行明确区分实际启动边界和异步回执，支持后续取消裁决设计。需要在解决两个高优先级问题时明确将“派发”拆成是否领取、是否启动确认、是否发生执行副作用三种可观察事件，避免测试和状态机使用不同含义。

## Shape fit — strong

单条用户旅程为内部排队工具保留提交至终态的主路径，主要篇幅用于能力、边界与验收条件。团队可以从 FR、AC、NFR 抽取架构与故事输入，且真机依赖已被约束在条件目标。
