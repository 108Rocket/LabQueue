## Foundation · 基础

面向不同研究组研究生的中文版内部桌面 Web，提供已认证提交者的三页操作。首版以模拟闭环为需求背景，真实 L20 派发仍受 FR-09 / AC-12 条件约束。视觉规则见 [DESIGN.md](DESIGN.md)。低保真参考见 [wireframes.md](wireframes.md)，出现差异时以 DESIGN.md 和本文件为准。

## Information Architecture · 信息架构

| 页面 | 入口 | 用户在此完成的任务 |
| --- | --- | --- |
| 提交任务 | 顶部导航、本人列表空态 | 填写自己的任务及显存估计。确认入队后进入我的任务或打开该任务详情。 |
| 我的任务 | 顶部导航、提交结果、详情返回 | 浏览本人的任务，核对队位、等待原因及当前状态，打开本人任务详情。 |
| 任务详情 | 本人任务行、提交确认后的详情链接 | 查看当前状态、失败原因和自己的任务配置，按取消资格操作。 |

`[ASSUMPTION]` 我的任务以便于回查为目的，示例将本人最近确认入队的任务置顶。实际队位读自最近一次确认的全局队列，从第 1 位起，只对仍在队列中的本人任务显示。调度顺序由确认入队序号决定。时间戳只供阅读，统一标出时区（示例用 UTC+08:00）。同时间、时钟回拨和重启均以 PRD 的入队顺序语义为准。FR-02、FR-03 / AC-01、AC-02、AC-10、AC-13。

| 组件 | 行为 |
| --- | --- |
| 顶部导航 | 两个入口依次为「提交任务」「我的任务」。详情页可返回我的任务。 |
| 任务表单 | `[ASSUMPTION]` 任务名与执行命令用于示例，字段核对见 Q6。提供「未知」「填写估计」两种显存选项，只有后者需填数值及单位。字段错误保留已填内容，未知值独立保存。FR-01 / AC-01、AC-02。 |
| 反馈区 | 使用 `{components.status-notice.background}` 承载当前问题。提交确认、查询错误、监测异常、取消请求和执行结果分别说明各自影响，短暂提示消失后仍可在对应状态区查到可确认的任务结果。 |
| 任务表 | 仅显示本人条目。任务名为可直接打开详情的链接，行内显示状态、队位（适用时）、原因和确认入队时间。显存未知可与任务名同组展示。表格字段到此为止，提交配置在本人详情中查看。FR-03、FR-08 / AC-01、AC-11、NFR-02。 |
| 任务状态区 | 使用 `{components.status-label.background}` 辅助识别当前状态。等待原因、上次确认、核对提示和取消反馈各有文字。详情与列表采用相同状态语义。 |
| 操作按钮 | 「提交任务」「刷新状态」「取消排队」用动作命名。`[ASSUMPTION]` 取消入口放在详情。取消处理中或结果未知时，详情状态区只提供「刷新状态」。服务端确认仍可取消且原请求已结束后，恢复「取消排队」。 |
| 取消确认框 | `[ASSUMPTION]` 显示任务名及「启动确认前可取消」。按钮为「返回详情」与「确认取消」。发送时可在按钮上反馈本次操作的进度。两页的任务状态按核对结果显示。FR-07 / AC-07、AC-09、AC-10。 |
| 任务配置 | 详情在所有权成立时显示自己的提交配置。若支持显示命令、工作目录或日志，均须按权限提供。未授权或不存在统一反馈「无法查看此任务」，响应及界面均无任务信息，且取消操作不得改变他人的状态。FR-01、FR-08 / AC-11、NFR-02。 |

## State Patterns · 状态与反馈

### 任务状态

| 用户可见状态 | 队位和反馈 | 取消排队 |
| --- | --- | --- |
| 排队中 | 已知位置显示「第 N 位」，并显示当前等待原因。GPU 监测异常作为等待原因，在队位能确认时可同时展示。 | 本人且仍符合取消条件时可发起。 |
| 已获准 | 已领取一张 GPU 的平台内使用权，清除当前队位。任务进入启动流程，实际是否开始执行由后续确认给出。 | 启动确认前仍可申请取消。竞态以服务端启动确认与取消确认的事务提交先后裁决。 |
| 运行中 | 已确认正在执行，显示自己的运行状态。 | 取消排队截止。 |
| 已完成 | 执行结束与成功结果得到确认。 | 无取消排队入口。 |
| 失败 | 执行结束与失败结果得到确认，显示可理解的原因。模拟 OOM 保留原参数，自动修改和重跑不在操作范围内。 | 无取消排队入口。 |
| 已取消 | 列表和详情在确认取消事务成功提交后显示「已取消」。任务退出队列。 | 无取消排队入口。 |

### 与任务状态并存的反馈

| 情形 | 展示与转移 |
| --- | --- |
| 监测异常：任务仍排队 | 显示具体监测原因。派发暂停。普通 GPU 占用有单独文案。 |
| 监测异常：任务已获准且未通过启动确认 | 新的启动确认被阻止。监测原因单独显示，任务状态按启动与取消的核对结果更新。观测恢复后根据最新有效观测及原排队顺序重新评估派发。FR-04 / AC-04、AC-05、AC-14、AC-15。 |
| 从未发起取消，启动状态待核对 | 两页均显示「启动状态待核对」。仅有启动待核对的证据时，也使用此文案。 |
| 已发起取消且取消结果未确认，启动状态待核对 | 两页均显示「启动状态待核对，取消尚未确认」。必须有已发起取消的证据，详情状态区只提供刷新。 |
| 启动待核对期间的资源提示 | 有监测异常时另行说明。即使 GPU 监测恢复，核实前也不得重新启动原任务或将其 GPU 派给其他任务。其他排队任务只见通用等待原因，例如「暂时没有已确认可派发的 GPU」。FR-04、FR-05、FR-07 / AC-07、AC-08、AC-14、NFR-01。 |
| 已确认启动，结束结果仍待核对 | 可显示「执行结果待核对」。结束结果获确认后显示相应终态。FR-06 / AC-03。 |
| 取消请求处理中 | 显示「取消请求处理中」。任务状态按已提交的结果展示，详情状态区只提供刷新。确认仍可取消且原请求已结束后恢复取消入口。 |
| 已确认取消事务成功提交 | 两页显示「已取消」，详情撤下取消按钮。晚到的旧回队反馈不得覆盖已确认的取消结果。 |
| 已核实未通过启动确认、未实际启动且未取消，回队事务已成功提交 | 两页显示「排队中」。回队沿用原入队顺序。两页显示服务端读取的当前队位与等待原因。回队事务提交前维持已确认状态。FR-02、FR-03、FR-04 / AC-13 至 AC-15。 |
| 启动确认事务先成功提交，取消被拒 | 两页反馈「已过取消截止点」，详情撤下取消入口。任务状态继续按已确认的执行信息更新。FR-07 / AC-07、AC-09、AC-10。 |

### 页面读取与提交反馈

| 页面 | 加载、空态和错误 |
| --- | --- |
| 提交任务 | 已登录时可填写。GPU 监测异常时派发暂停，任务仍可提交并等待。`[ASSUMPTION]` 发送期间显示「正在提交」并暂时禁用按钮。收到入队确认后才显示「已入队」；明确拒绝时保留输入并说明原因；响应中断时显示「提交结果暂未确认」，提供「查看我的任务」。安全地恢复或再次提交见 Q6。 |
| 我的任务 | 首次显示「正在加载我的任务」。确认空列表后显示「还没有任务」和提交入口。查询失败时显示「暂时无法刷新任务状态」。同一已授权会话中已有的本人状态、队位和等待原因标为「上次确认」。首次失败时保留重试入口。 |
| 任务详情 | 加载期间先显示通用提示，确认访问权限后才显示数据。刷新失败时显示「暂时无法刷新任务状态」，已有本人状态、队位和等待原因标为「上次确认」。取消处理中或结果未知时，状态区只提供刷新。恢复取消入口须读取服务端当前的资格和请求结果。失去访问权限时撤去任务数据和动作。 |
| 所有页面 | 会话无效时使用通用登录提示。未授权详情与取消反馈不包含任务是否存在、其他人的标识、命令、工作目录、环境变量、日志或结果。FR-01、FR-08 / AC-11、NFR-02。 |

## Interaction Primitives · 操作

- 列表与详情的「刷新状态」、重新打开页面和浏览器返回均重读服务端已提交状态。恢复时根据可确认的取消请求信息选择待核对提示。
- 启动确认与取消确认以服务端事务先成功提交的一方为准。点击顺序与回执到达顺序只反映交互过程。取消请求超时、回执缺失或监测恢复时继续按已提交的状态展示。
- 读失败时，已有的任务状态、队位和等待原因标为「上次确认」。晚到的旧响应不得覆盖已展示的更新状态。

## Accessibility Floor · 无障碍底线

- 表单有常驻标签与错误说明。键盘可提交、查看详情、刷新及确认取消。焦点清晰可见并按阅读顺序移动。
- 确认框打开时聚焦「返回详情」，Escape 退出尚未提交的确认。关闭后回到发起控件，控件已撤下时回到任务状态区。
- 状态、按钮不可用原因、字段错误用文字传达。屏幕阅读器可获知实质状态变更，同一次手动刷新且结果相同不重复播报。
- 缩放或长文案使内容折行时，保留标签、状态、动作和完整原因。视觉焦点和对比度目标见 [DESIGN.md](DESIGN.md#colors--色彩)。

## Key Flows · 场景走查

以下是合成示例。A 属于林妍，B 属于另一组的周宁，每人只在自己的会话中看到自己的任务。

### UJ-01 等卡并获得结果

1. 林妍在提交页选择显存未知。两卡都忙，她收到入队确认，随后在我的任务看到 A 排第 1、GPU 正被占用。周宁稍后入队，从他的会话看到 B 排第 2。FR-01 至 FR-03 / AC-01。
2. 有一张卡经有效观测确认可派发。A 显示「已获准」，B 显示第 1 位。林妍打开详情核对运行状态。确认入队时间相同或回拨也由系统确认序决定顺序。FR-02 至 FR-04 / AC-02、AC-13。
3. **核对点。** 林妍看到「运行中」，随后在结束获确认时看到「已完成」。另一个模拟分支显示「失败：GPU 显存不足」，原参数保留且只启动一次。FR-06 / AC-03。

### 观测失效后恢复

1. 周宁在排队中依次核对三种模拟分支的等待原因：监测失败、观测过期、外部占用不明。旧的可用观测不能用于派发。FR-03、FR-04 / AC-04、AC-05。
2. 另一个分支中，林妍的 A 获准后遭遇观测异常。旧领取无法通过启动确认。系统核实 A 未通过启动确认、未实际启动且未取消。回队事务成功提交后，两页按 A 的原入队顺序显示当前队位和监测阻塞原因。
3. **核对点。** 监测恢复后，A 依据最新观测先获准，可能改用另一张卡。旧领取无法启动。如果取消确认已先成功，刷新仍显示「已取消」。FR-04 / AC-14、AC-15。

### 取消与启动竞争

1. 林妍打开自己的排队中或已获准任务，点击「取消排队」并确认，看到「取消请求处理中」。FR-07 / AC-09、AC-10。
2. **核对点。** 取消确认事务先成功提交时，两页显示「已取消」。启动确认事务先成功提交且取消被拒时，两页反馈「已过取消截止点」。若已发起取消但回执缺失，启动和取消仍待核对，两页显示「启动状态待核对，取消尚未确认」，详情只提供刷新。服务端确认仍可取消且原请求已结束后恢复按钮。FR-07 / AC-07、AC-09、AC-10，NFR-01。

### 启动与取消仍待核对

1. A 的启动未知。林妍从未发起取消时，两页显示「启动状态待核对」。另一个分支中，林妍已发起取消但结果未确认，两页显示「启动状态待核对，取消尚未确认」。周宁只看到本人的队位与通用等待原因。
2. **核对点。** 若刷新失败，两页把旧队位标为「上次确认」。若读取到更新的取消或回队结果，晚到的旧响应不能覆盖。核实 A 未通过启动确认、未实际启动且未取消后，仍须等回队事务成功提交，才显示「排队中」及按原入队顺序得到的当前队位和等待原因。FR-02 至 FR-05、FR-07 / AC-07、AC-08、AC-14、AC-15，NFR-01。

### 跨用户访问

1. 周宁在自己的列表里只能看到 B。周宁打开 A 的已知链接或尝试取消 A，得到通用反馈。同组非所有者对 A 做同样操作时，反馈一致。
2. **核对点。** 界面与响应都没有 A 的配置、日志、名称或状态，A 的队位和租约也不发生变化。未认证及伪造身份的用例适用同样的权限边界。FR-01、FR-08 / AC-11，NFR-02。
