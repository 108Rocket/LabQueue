# LabQueue 产品简报草稿

这是整理已有用户陈述的输入草稿。尚未完成 `bmad-product-brief` 工作流、团队评审或课程 M1；建议的指标和方案仍需确认。

## 问题与目标用户

每位研究生都需要使用共用服务器。服务器包含两张 L20，不同研究组共同使用；人工协调容易碰到排队不透明、同时抢卡、组间争用和首次显存未知的问题。部分人直接使用服务器，没有接入平台或不遵守约定。

项目希望提供统一排队入口，帮助愿意接入的研究生提交任务、了解等待状态，并选择合适的 GPU。对未接入的任务，平台需要观察实际占用，保守避让并说明原因。

## 用户已确认的约束

| 编号 | 约束 | 依据 |
| --- | --- | --- |
| BR-01 | 一台服务器，两张 L20 | 用户明确回答“同一台服务器，两张 L20” |
| BR-02 | 普通用户权限部署 | 用户明确回答“只能以普通用户权限部署” |
| BR-03 | 目标用户是每位研究生，服务器上有不同组 | 用户补充了全体研究生与多组场景 |
| BR-04 | 考虑未接入平台或不遵守规则的人 | 用户明确要求考虑绕过入口的情况 |
| BR-05 | 首次运行显存占用可能未知 | 用户明确指出首次启动显存未知 |
| BR-06 | 本项目先在本地搭建，无需 V100 | 用户对本次环境搭建的明确指示 |

## 建议的首版范围，待 PRD 评审

1. 账号、可信组成员关系、任务所有权与隐私。
2. 提交、取消和查询排队任务，展示平台任务与可观察的外部占用。
3. 两卡分配、一卡一个平台任务、未知显存的保守准入和故障恢复。
4. 组间公平与组内排序、使用统计、审计记录。

这些是候选 Epic，不代表已经满足“≥3 Epic、≥12 Story”的课程要求。应在 PRD 与架构评审后拆分成能写出测试断言的 Story。

## 成功度量建议，待确认

- 并发提交和重复领取时，同一 GPU 只有一个有效平台租约；拟以 200 个并发领取请求中重复租约数为 0 验证。
- 资源监测失效、权限不足或数据过期时，新分配数为 0；恢复后只能依据新鲜观测重新判断。
- 建议队列查询在 50 个并发查询、1,000 个任务记录的指定测试环境下 P95 ≤ 500 ms；环境、持续时间和测试方法在 PRD 中固定。
- 建议在可控模拟场景中，持续等待的组在其他组重复获取新空闲卡前得到轮转机会；需明确组权重、组内顺序、例外和公平算法。

以上是候选验收指标，尚未测量；不能据此承诺真实服务器等待上限或 GPU 完全独占。

## 建议的关键设计问题

- 外部进程可在“检测空闲”与“启动任务”之间抢占 GPU。普通权限下只能重新检测、谨慎启动并处理冲突，无法消除竞态。
- 若研究生有不同 Linux 账户，需考虑每用户代理或用户主动执行。普通账户的中心服务无法代替所有人切换身份。
- 未知显存任务初次申请整卡的平台使用权，实际运行时记录采样峰值。模型、输入、batch、精度等改变后旧记录不再直接用于准入。
- 组间轮转、组内用户轮转/FIFO 可作为候选；仅按一次启动次数公平会忽视长短任务，应比较 GPU 时间等记账方案。

## 首版范围外建议

管理员权限改造、强制阻止绕过平台、终止别人进程、多服务器集群调度、分布式多卡训练调度、自动改 batch 重试、同卡多任务显存拼装、自动预测所有任务真实峰值。
