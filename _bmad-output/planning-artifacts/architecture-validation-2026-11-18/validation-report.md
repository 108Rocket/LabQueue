## 三条时序

| 场景 | 按现有正文走查 | 追溯 |
| --- | --- | --- |
| 取消与启动同时到达 | **先成功提交者胜**，不是先收到请求或回执者。取消先提交：同次提交进入已取消、撤销领取、释放租约，启动事件为 0。启动先提交：唯一模拟启动事件与确认同提交；排队取消返回已过截止点，不释放；确认执行结束且不会再用卡才释放。 | AD-1/3/4/6；FR-05/06/07、NFR-01；AC-07/10/03 |
| 监测恢复与旧领取 | 失效推进代际或封闭单卡未确认领取；新观测不复活旧领取。证实未启动且封闭旧路径后，事务重查任务和领取，解除旧租约并用原 `enqueue_seq` 回队；取消先提交则迟到回队无效。按最新观测发新领取 ID，A 仍排在 B 前，可改领 GPU 2，旧请求不能改写新租约。 | AD-2/3/4/5/6；FR-02/04/05/07、NFR-01；AC-05/13/14/15 |
| 结果未知、超时、监测显示空闲 | 超时只触发核对。A 的原 GPU UUID 和租约仍留在当前租约表、继续占唯一名额；新鲜空闲观测不是执行证据。B 不能领取原卡，A 不得重发启动或换卡启动；恢复可信证据后才按同一领取的回队或终态规则处理。 | AD-3/4/5/6；FR-04/05/06、NFR-01；AC-08 |

## 阻塞项（待人工判断）

### B1 · 模拟：启动确认未知时，取消、启动与保留缺少共同判定

- **证据**：[AD-4](../architecture.md#L59) 按“尚未启动确认”定义取消，[AD-6](../architecture.md#L74) 要求证据未知时只核对、保留原卡。迁移表启动行还漏写 AD-4 的“未进入待核对”，待核对本身只是可见性状态（[表](../architecture.md#L94)）。已明确完成确认、仅回执丢失的任务不受歧义影响：它已过取消截止点。
- **反例**：A 仍显示已获准、确认事实暂不可核实，监测恢复。取消端若把“查不到确认”当成“确认未发生”，可成功取消并解除 GPU 1；核对端却要求继续保留。反过来，若把所有待核对一律视为不可取消，会挡住本可在事务内证实未启动并撤销的本人任务。启动端也不能仅凭“当前租约仍在、最新观测有效”放行。唯一启动事件防重复，不代替这些前置条件。
- **建议裁决**：区分确认已提交、可在事务内证实未确认且未启动、证据未知。前者拒绝排队取消；第二种允许本人用同一次提交封闭启动路径、取消并释放；第三种返回待核对而非取消成功，保留原卡且不发新启动。AD 与迁移表共用同一谓词。是否记录取消意图另议，不能显示已取消。
- **关联与断言**：AD-1/3/4/6；FR-04/05/07、NFR-01；在 AC-07/08/10 加交叉分支：未知时叠加本人取消和旧启动重放，取消成功数、解除数、同卡新派发数、新增启动数均为 0；恢复证据后分别验证已确认和确定未确认两条路径。不改现有 AC 编号。

### B2 · 模拟：启动事务的观测到期与旧领取校验未完全绑定

- **证据**：[AD-5](../architecture.md#L66) 在取得写权后检查单调时钟，并明确旧领取永久失效；[AD-4](../architecture.md#L59) 以事件提交为模拟启动，但未明确初检通过后、确认提交前越过有效期的裁决。事务能串行化快照写入，不能阻止单调时钟前进。单卡从外部占用恢复为空闲时，迁移表的“当前领取仍有效”也不应只靠当前租约存在和新样本空闲就得出。
- **建议裁决**：写明观测有效性在哪个裁决点成立，以及最后检查到提交之间跨过有效期时如何关闭准入；把原领取的持久失效状态或代际比较列为启动硬条件。不要用新样本覆盖该领取的失效证据，也不要把一次提交前读时钟声称为已证明提交时刻有效。
- **关联与断言**：AD-1/3/4/5；FR-04/05、NFR-01；扩展 AC-14/15：先通过观测初检，再推进可控时钟越过有效期、恢复事务，断言无启动确认和启动事件。另测单卡外占→恢复空闲、旧租约尚未解除时重放旧领取，确认和启动仍为 0；新领取才能启动。

### B3 · 仅阻塞真实 L20 启用：每用户代理尚无启动边界和宿主证据

- **证据**：[AD-8](../architecture.md#L88) 明确为本人 Linux UID 下的条件候选，不是模拟依赖，也未授权共享后端代跑。在线裁决、代理持久尝试记录与创建 OS 进程之间仍需协议与故障证据；异步回执不能作为取消截止点。[部署开关](../architecture.md#L110) 已要求不确定时停用。
- **建议裁决**：维持默认关闭。启用前用目标主机普通权限核验账号/UID、凭证、GPU UUID 和外部占用可见性；覆盖裁决前后、创建进程前后、回执丢失、代理重启或换代，证明旧领取不能延迟兑现或重复创建进程，未知时仍保留原卡，且有可核实的进程归属与结束证据。此项不阻塞模拟门槛。
- **追溯**：AD-5/6/7/8；FR-04/05/07/08/09；AC-12（条件验收）。NFR-01 的模拟证据不能外推为真实执行结论。

## 建议（不改动 PRD 编号）

- **S1 · 恢复与调度真正并跑。** AD-2/3/5/6；FR-02/04/05、NFR-01；AC-14/15。AD-5 已要求先处理需回队的旧领取，迁移表的“领取”行未列此条件。将它放进领取事务，或同事务先完成可证实的回队再取队首。扩展 AC-15：发布恢复观测时暂停回队，先让 B 争唯一新可用卡，再验证应回队的 A 先领，且旧请求失败。结果未知不等于已证实可回队；启动确认也未知的较早任务是否阻挡其他卡的领取需显式定界，绝不能因此解封原卡。
- **S2 · 补足故障断言。** AD-1/3/4/6；FR-05/06/07、NFR-01；AC-03/07/08/10。取消先提交要核对同提交撤销领取、释放租约，取消应答丢失后重放不得二次释放。启动先提交要在结束前核对租约仍在。AC-08 要确认被测核对者确实得不到可信执行证据（只丢回执不够）；恢复证据后，已启动分支的历史启动数仍为 1，终态释放恰好一次。验收观察记录不能被系统用来提前裁决。
- **S3 · 同组隔离相符，验收覆盖各入口。** AD-7；FR-01/08、NFR-02；AC-11。同组不授予列表、详情、取消或私有输出权限；服务端取可信所有者，写事务内再验权。用已知任务 ID、伪造用户/组、同组/异组/匿名覆盖列表、详情、取消响应和输出引用，检查无私有标记泄漏且任务状态、顺序和租约未变化，另用本人读取/取消作正对照。
- **S4 · 核验每条写连接的事务配置。** AD-1/3；FR-04/05、NFR-01；AC-06/07/08。让两条独立应用连接确认：关键读取前实际执行 `BEGIN IMMEDIATE`，每条写连接 `synchronous=FULL`，库处于 `WAL`。记录实际 SQLite 版本并核对 WAL 修复。项目上下文的 Python 旧版本评审后再同步，不是模拟设计阻塞。
