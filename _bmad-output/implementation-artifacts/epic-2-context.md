# Epic 2 Context: 从可靠观测派发并取得执行结果

<!-- Compiled from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

用两张可控的模拟 GPU 验证队首任务从资源准入、领取、唯一启动到结果确认和释放租约的完整路径。观测不可靠时暂停派发并向任务所有者说明等待原因，恢复后只根据最新有效观测评估容量。

## Stories

- Story 2.1 · 等待有效观测并按最新快照恢复派发
- Story 2.2 · 原子领取队首和单卡租约
- Story 2.3 · 让一次启动确认只产生一次模拟启动
- Story 2.4 · 查看完成或失败并释放租约

## Requirements & Constraints

- 两卡按固定 GPU UUID 区分。已认证的任务可用未知显存估计排队并申请整卡，跨组按持久入队序号排队。外部占用已确认的卡不能领取，每卡同时最多一个平台租约。
- 监测失败、设备漏报、快照过期或外部占用不可确认时，暂停新增领取和未确认启动。恢复只采用完整且顺序有效的新快照。模拟验收覆盖两卡可用性互换，核对恢复后的候选卡和后续领取使用的稳定标识一致。
- 任一任务最多一次模拟启动。执行事实未知时保留原卡。确认该次执行已结束并且无法继续用卡后，记录完成或失败并释放。模拟 OOM 向本人提供显存不足的诊断，保留原参数。
- 以合成账号、可控时钟、故障注入和已提交事件验证一致性。真实 L20 派发是独立的条件目标，须另行核验服务器上的监测可见性、本人执行身份和故障边界。

## Technical Decisions

- 任务、观测、模拟时钟、租约和执行事件共用同一个本机 SQLite 数据库。启用 WAL 和 `synchronous=FULL`。关键前置条件在 `BEGIN IMMEDIATE` 后重读；提交后才发布结果。探测位于事务外。提交结果未知时换连接读取已提交状态，核实后再决定是否重试。
- 一个发布者发布完整双卡快照，旧发布代际和乱序样本无权覆盖。权威模拟时钟在写事务内单调推进，时效从采集开始计算，达到截止点即过期。全局失效与准入代际推进同提交；重启先封闭旧代际，已确认启动与原租约保留。确认单卡被占用时撤销该卡未确认领取的启动资格，新观测不恢复旧资格。
- 领取事务重读队首、已核实应优先回队的任务、当前准入和租约。已获准状态、全新领取 ID、GPU UUID、准入代际和租约同提交；数据库约束当前租约的 GPU UUID 与任务 ID 分别唯一。启动事务复核身份、领取、原卡、时效与持久执行证据，与取消按提交次序裁决；启动确认和按任务 ID 唯一的模拟启动事件同提交。
- 恢复事务在持有写权后重新核对任务、领取、原卡和执行证据。证实未确认启动、未启动且未取消时，封闭失效领取、释放原租约并按原序回队；重新领取使用新 ID。证据未知期间不释放、不重复启动。终态及释放须同提交。

## UX & Interaction Patterns

- 本人列表和详情使用相同语义，显示当前队位及具体等待原因。区分观测失败、观测过期、外部占用不明及正常资源占用；估计启动时间留空。准入关闭时仍可提交与查看本人任务。
- 在同一已提交读快照中读取队位、等待原因和全局页面版本，原因变化与版本递增同提交。列表和详情在同一登录会话共享已见版本下限，旧响应无法覆盖新状态。查询失败时将既有数据标为「上次确认」。
- 领取后显示「已获准」，按已确认事实更新运行或终态。只有本人可查看任务失败诊断和私有输出。

## Cross-Story Dependencies

- 2.1 独立验证持久模拟时钟、双卡观测异常准入与恢复后的候选卡。2.2 复用这套状态执行领取，再验证异常期间新增领取为零、恢复后仅用最新可用卡领取，并与 1.2 联调 FIFO。
- 2.3 复用 2.1 的准入和 2.2 的领取、租约，2.4 消费当前执行结果。取消与启动竞态由 Epic 3 联调，过期与启动提交顺序、失效领取回队及跨重启综合证据由 Epic 4 补齐。
