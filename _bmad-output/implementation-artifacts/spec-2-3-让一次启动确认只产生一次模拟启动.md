## 意图

为本地双卡模拟的已获准任务提供唯一启动裁决，依据 FR-04、FR-05、NFR-01、AD-1/3/4/5、AC-06/07。给定有效的当前领取及原租约，启动在取得 SQLite 写权后复查任务、执行身份、GPU UUID、准入代际、单卡资格、持久模拟时钟与执行证据。条件成立时同提交记录确认与按任务唯一的启动事件，保留原租约。丢失回执后重放匹配的请求须读到原确认，启动数仍为 1。以过期、失效、取消、待核对、证据不明及身份或标识不匹配请求启动，新增确认、事件与租约变更均为 0。

</frozen-after-approval>

## 实现记录

- 复用 `observations.py` 的事务内时效复核、`leases.py` 的持久领取和执行证据、`submissions.py` 的写事务与只读连接。进程内入口用可信合成账号的所有者 ID 校验模拟执行身份。
- 新表保存启动事件与原回执，同事务更新执行证据、任务运行状态与快照版本。本人列表及详情显示运行中。

## 本地双卡验证

| 场景 | 已提交状态的断言 |
| --- | --- |
| 双卡正常启动、同一领取并发重放 | 两个任务分别使用原卡的稳定 UUID，各一条事件。重复调用返回同一回执，两个原租约仍有效。列表与详情显示「运行中」，迟到的「已获准」快照不覆盖新状态。 |
| 单卡并发领取后重试（AC-06） | 两个领取者实际争同一张空闲卡，分别覆盖领取回执正常与丢失。随后重试领取和启动，租约历史只有一条且原保留区间未改，早到任务启动 1 次，后到任务继续排队且启动 0 次。 |
| 提交成功、回执丢失 | 故障点执行真实 SQLite `COMMIT` 后关闭原连接。新只读连接读回原事件。使首次核对也失败时，重放仍读回同一确认。随后让观测过期，并将执行结果置为待核对，已有启动确认仍可读回，累计启动数为 1。直接插入同任务的第二条事件被唯一约束拒绝。 |
| 提交前连接关闭、事务部分写入失败 | 前者核对无原结果，仅尝试一次写事务。后者在确认和事件已写入事务后故意拒绝任务状态更新，确认、事件、任务状态和版本一起回滚。 |
| 观测过期、查询失败、外部占用不明 | 均拒绝启动，启动确认、事件与租约变更各为 0。SQLite 忙锁重试取得写权后可读到刚提交的到期状态。若故障夹具将时钟推进至截止点但缺失过期标记，启动事务会补记过期并推进准入代际。 |
| 领取失效 | 新观测恢复后旧代际和单卡资格撤销仍阻断启动。已解除的租约也不接受请求。三种情形均无新增确认、事件或租约变更。 |
| 已取消、待核对、执行证据不明 | 分别注入已提交状态。待核对用例同时持有明确未启动证据，仍拒绝。未知证据、有已启动或已确认标志但缺失事件也拒绝。首次执行裁决时 SQLite 拒绝读取持久事件，事务回滚。以上情形均无新增确认、事件或租约变更。 |
| 执行身份或标识不匹配 | 同组其他执行身份、错误任务 ID、领取 ID 或 GPU UUID 均被拒绝，新增确认、事件与租约变更各为 0。 |
| Story 2.2 库升级 | 已有任务和租约原样保留，新增的启动事件表为空。初始化推进代际后，即使重新发布有效观测，旧领取也不能首次启动。 |
