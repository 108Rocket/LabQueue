# Epic 3 Context: 在启动边界内撤回，并安全处理待核对

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

让提交者在启动确认前撤回自己的任务，并在回执丢失、重启或执行事实未知时查清撤回结果。队位和卡的可用性随已提交的裁决更新，使其他任务能按原序使用真正释放的容量。

## Stories

- Story 3.1: 取消尚未领取的排队任务
- Story 3.2: 裁决已领取任务的取消与启动竞争
- Story 3.3: 启动事实未知时保留原卡，证据恢复后按事实裁决

## Requirements & Constraints

- 在本地双卡模拟中按持久记录取证。每个任务至多启动一次，每张卡至多一个当前平台租约。取消生效后启动数为零；执行状态未知期间，原卡新增派发数为零。
- 只允许可信会话中的所有者取消或封存。写事务内复核任务归属，Cookie 写操作核验跨站请求。同组、异组和未认证会话分别作为负对照；他人任务与不存在的任务返回一致的资源不可访问反馈。越权成功、私有标记泄露及未授权写入均应为零。

## Technical Decisions

- 用同一 SQLite 数据库取得写权后核对所有权、队列状态、当前领取及启动证据。取消先提交时，原请求终局与任务退出队列同提交；存在匹配领取时同提交封闭领取并释放原卡。启动确认先提交则记录已过截止点。启动事实未知则保留原卡，持久记录执行待核对及本次未取消的终局。
- 以所有者、任务和取消请求 ID 联合定位受理记录。受理与终局分别持久化，受理自身不决定竞态。重启后由服务端按当前证据推进已受理未终结的原 ID。只有本人明确发起核对命令时才可封存未受理 ID；与受理争用同一写权并复查。旧 ID 已封存或终结后重放只返回原结果，不推进版本或再次操作任务与租约。
- 状态、请求结果、队位、等待原因和取消资格的可见变化与全局页面版本同提交。本人队位按仍排队且入队序号更小的任务数计算。读取页面时在同一快照中投影结果、队位和版本。

## UX & Interaction Patterns

- 普通刷新只读。未查到原 ID 显示未知，已受理但尚无终局显示处理中。核对确认框说明继续后可封存未受理请求；打开、关闭与返回均不发送命令。只有服务端确认取消生效才显示「已取消」。
- 列表与详情在同一会话共享已见版本下限与待核对 ID。低版本画面标「上次确认」，局部回执仅核对匹配 ID。仅当完整快照同时证明原 ID 已封存或终结、且任务当前可取消时恢复入口。用户手动再发时使用新 ID。

## Cross-Story Dependencies

- Epic 1 提供可信身份、本人快照及全局 FIFO；Epic 2 提供双卡准入、领取、启动和租约证据。3.1 联调取消后的下一任务领取；3.2 补齐已领取的本人取消正对照与截止点裁决。
- 3.3 验证启动事实不可读时的保留；待 4.2 提供回队入口后，再联调原领取的恢复资格。跨重启和重放的综合 NFR 证据归入 4.6。
